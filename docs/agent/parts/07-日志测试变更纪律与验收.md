## 16. 日志、诊断与可测试性

1. 关键状态转换必须记录：旧状态、新状态、原因、触发事件、任务 ID、运行代次和时间。
2. 节点检索记录命中证据、失败类型和耗时，不应只记录“找到/没找到”。
3. 手势记录 GestureCommand ID、坐标上下文、派发结果、回调结果和取消原因。
4. 人工接管记录每一轮接管周期 ID、暂停原因、静默判定、恢复校验结果和最终动作。
5. 服务生命周期记录应区分权限、绑定、初始化和业务运行状态。
6. 日志不得依赖单一自由文本；关键状态应使用可检索的结构化字段。
7. 时间、随机数、调度器和平台 Gateway 应尽可能通过接口注入，便于单元测试。
8. Domain 和 Application 应能在不启动真实 Android Service 的条件下测试核心规则。
9. 不得为了方便测试而将生产状态所有权转移给测试辅助类。

## 17. 代码保护与变更纪律

### 17.1 修改前

每次修改前必须：

1. 阅读本文件中与任务相关的架构边界和保护规则。
2. 检查当前源码，确认实际类、调用链、状态所有者和已有测试。
3. 区分“目标组件”与“当前实现类”，建立映射，不得凭类名猜测功能。
4. 确认变更范围及其对现有默认配置、持久化、权限、广播、UI 和业务算法的影响。
5. 对超出用户任务范围的改动保持克制，不顺手重构无关模块。

### 17.2 修改中

- 不破坏 Freedom 现有能力、默认配置、UI 交互和运行逻辑；逐步增加业务。
- 不重写 AccountBrowse 算法。
- 不改变阶段顺序、识别阈值、延时、重试次数、手势路径参数、人工接管和恢复规则，除非该项变更被独立确认并记录。
- 不改变现有持久化 key、默认开关、权限声明、广播 Action 和既有 UI 交互，除非该阶段明确需要且有单独验证。
- 不为架构整齐而一次性搬迁大量文件。
- 新增代码应有清晰职责、单向依赖、可测试边界和易懂的中文注释。
- 不创建没有实际用途的大量空目录、空接口或空类。
- 不将不同业务领域的状态塞入一个全局可变对象。
- 不得以删除规划中的组件、职责或目录来掩盖当前源码与目标架构的差距。

### 17.3 修改后

必须完成与改动规模相匹配的验证，并报告：

1. 修改文件及每个文件的实际变更；
2. 对应的目标架构组件；
3. 原有行为是否保持；
4. 新增或调整的状态转换和调用链；
5. 执行的测试、构建命令及其结果；
6. 未能验证的部分及原因；
7. 当前源码与目标架构仍存在的差距。

测试失败或构建未完成时，必须如实说明，不得声称已通过。

### 17.4 必须独立确认的重大变更

以下变更不得作为普通整理顺手实施：
- 改变 AccountBrowse 已验证算法或用户可观察行为；
- 改变全局 RunMode 互斥规则；
- 改变人工接管/恢复判定；
- 改变持久化 key、数据结构兼容策略或消息去重语义；
- 改变权限声明、广播 Action、默认开关或现有 UI 交互；
- 改变手势唯一执行通道、坐标算法或可视化强制要求；
- 将当前单体提前拆分为多个 Gradle Module；
- 删除或合并目标架构中的规划组件。

## 18. Agent 执行完成的验收标准

一项工程任务只有在下列适用条件得到核对后，才可报告完成：
- [ ] 当原文的技术实现方式存在问题时，应该修正实现方式，而不是直接取消它所要达到的工程目标
- [ ] 不得删减或弱化目标架构。
- [ ] 变更没有突破领域职责边界和状态所有权。
- [ ] FreedomAccessibilityService 未承载业务状态机或 AI 业务逻辑。
- [ ] 无障碍权限、悬浮窗权限、服务绑定、初始化和业务运行状态没有混为一谈。
- [ ] 节点检索有包名/事件过滤、频率边界、超时和失败处理。
- [ ] 所有屏幕手势通过 `dispatchGesture()` 执行，并处理完成/取消回调。
- [ ] 点击、轨迹、时间和起止点参数遵守本规范。
- [ ] 输入流程包含文本校验和发送结果核验。
- [ ] Memory Buffer 保留用户 ID 与文本哈希，Cooldown 和 UNKNOWN 状态可用。
- [ ] 自动手势有实时可视化，预览与执行共用同一命令数据。
- [ ] 人工接管每一轮都能独立暂停、静默判断、重新校验和恢复。
- [ ] AI_REPLY 与 ACCOUNT_BROWSE 保持隔离。
- [ ] 群聊、媒体消息、系统通知和方向不确定消息不会自动回复。
- [ ] 没有改变未经授权的现有功能、配置和交互。
- [ ] 测试、构建及未验证项如实报告。
