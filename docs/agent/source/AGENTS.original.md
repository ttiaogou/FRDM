# AGENTS.md — Freedom 工程架构与执行规范

> 基准来源：`Freedom.txt`（版本 1.0，整理日期 2026-11-10）  
> 本文件用途：将 Freedom 已确定的长期架构、行为边界和代码保护要求转化为 Agent 可执行的工程约束。  
> **本文件是目标架构与实施规范，不是对当前源码结构的描述。**

---

## 0. 最高执行原则

### 0.1 架构基准不可被当前实现反向删减

1. `Freedom.txt` 定义的总体架构、目标逻辑目录、组件职责、状态所有权和行为边界，是 Freedom 的长期工程基准。
2. 当前源码是实施对象，不是重新定义目标架构的依据。当前代码尚未实现某个规划组件时，应标记为“未实现/待建设”，不得因此删除该组件或缩减目标目录结构。
3. 当前源码与目标架构不一致时，必须记录：
   - 目标组件及其目标职责；
   - 当前由哪些类、文件或调用链承担相关职责；
   - 已实现、部分实现、未实现或存在职责混杂的状态；
   - 后续对齐方案及其对现有行为的影响。
4. 不得仅为追求类名一致、目录整齐或形式上的架构完整而进行大规模改名、搬迁或重写。
5. 架构演进应渐进进行。先确保现有行为不回退，再逐步建立清晰的模块边界和依赖方向。

### 0.2 技术修正不得取消原始目标

当原规范与 Android 平台能力、API 实际语义或当前实现发生冲突时：

1. 明确标记“冲突/需决策”或“技术表达需修正”。
2. 说明冲突发生的位置、平台限制、影响范围和可选实现。
3. 优先寻找能够保留原目标的实现方式。
4. 不得用“技术上不方便”“当前没有实现”或“更简单”为理由，擅自删除原有目标。
5. 未经用户明确授权，不得改变原有业务行为、默认配置、UI 交互、持久化契约或已验证算法。

### 0.3 项目范围说明

坐标扰动、轨迹参数化、等待时间分布和输入节奏，是本项目内部交互执行、操作稳定性、节律控制及输入检查的工程要求。不得擅自将这些要求解释为设备身份伪装、平台风控绕过、反作弊规避或第三方检测对抗，也不得自行扩展为这些目标。

## 1. Freedom 总体架构（长期基准）

### 1.1 架构名称

**Accessibility-Centric Modular Monolith with DDD + Clean/Hexagonal Architecture + Event-Driven Design**

中文：以无障碍能力为中心的模块化单体架构，使用领域驱动设计划分业务，使用整洁架构和六边形架构隔离依赖，并使用事件驱动完成内部模块通信。

### 1.2 各架构思想的职责

1. **Modular Monolith（模块化单体）**
   - 整个 Android 应用先保持一个 APK、一个主要进程和一个 `app` Gradle Module。
   - 代码在逻辑上严格模块化。
   - 只有当模块边界稳定、依赖清楚、构建收益明确时，才考虑将部分包提取为独立 Gradle Module。

2. **DDD（领域驱动设计）**
   - 按业务边界划分 Runtime、AccountBrowse、AIReply、Conversation 等领域。
   - 每个领域管理自己的业务模型、规则和状态。
   - 其他领域不得直接修改本领域内部状态。

3. **Clean Architecture（整洁架构）**
   - 业务规则不依赖 Android 系统、具体数据库、网络库或模型 SDK。
   - 业务层通过接口表达所需能力，外部实现由基础设施层提供。

4. **Hexagonal Architecture（六边形架构 / Ports and Adapters）**
   - Android 无障碍能力、陌陌、小红书、AI API、数据库均作为外部适配器。
   - 核心业务通过 Port/Interface 使用外部能力。

5. **Event-Driven Design（事件驱动）**
   - 无障碍事件进入统一事件入口，经过过滤、归一化、分流后到达对应业务。
   - 业务内部使用明确的事件和状态转换，避免多个模块互相直接调用内部方法。

6. **MVVM / MVI（界面状态管理）**
   - UI 仅展示状态和提交用户意图。
   - UI 不直接操作无障碍节点，不直接调用模型 API。

### 2.1 目录职责

- `core`：平台公共能力、运行管理、事件契约和日志，不承载具体业务规则。
- `features`：业务领域及其应用流程。自动浏览和 AI 回复同级、互相隔离。
- `adapters`：对外部系统的适配实现。陌陌页面细节不进入 AI 核心。
- `data`：持久化实现。Domain 不直接依赖具体数据库。
- `ui`：界面和状态呈现。
- `app`：应用组装入口，负责创建依赖关系，不承载业务逻辑。

### 2.2 目录与 Gradle Module 的关系

- 上述结构首先是逻辑包结构，不是要求立即拆成多个 Gradle Module。
- 不得为了“模块化”提前引入不必要的多模块构建复杂度。
- 只有模块边界稳定、依赖清楚、构建收益明确时，才提出 Gradle Module 拆分。
- 不得为了当前代码尚未迁移而删掉目标目录或组件。

## 3. 关键架构边界与状态所有权

### 3.1 `FreedomAccessibilityService`

唯一职责：实现 Android `AccessibilityService` 生命周期和系统回调入口。

负责：
- 服务连接、断开和系统回调；
- 接收无障碍事件；
- 取得当前窗口的短期访问能力；
- 将事件转交给统一入口；
- 在适当时机释放临时资源并记录生命周期。

不负责：
- 自动浏览状态机；
- AI 请求；
- 聊天上下文；
- 消息去重；
- 具体业务策略。

### 3.2 `AccessibilityGateway`

- 为业务提供受控的无障碍能力入口，例如读取当前窗口快照、查找可见节点、执行输入和手势。
- 对外暴露稳定接口。
- 不把 `AccessibilityNodeInfo` 等 Android 节点对象作为长期业务数据传递或持久化。
- 需要跨回调、排队或持久化的数据，应转换为普通数据快照和稳定标识。

### 3.3 `AccessibilityEventRouter / Policy`

- 负责事件过滤、分类、去重、优先级和路由。
- 普通页面内容事件、窗口切换、点击、滚动、触摸等事件采用不同处理策略。
- `AI_REPLY` 下不进入 AccountBrowse 的人工操作暂停/恢复控制器。
- `ACCOUNT_BROWSE` 下保留现有自动浏览的事件和人工接管规则。

### 3.4 `RunCoordinator`

是运行模式和运行状态的唯一所有者。

负责：
- 模式：`NONE`、`AI_REPLY`、`ACCOUNT_BROWSE` 等；
- 状态：`STOPPED`、`STARTING`、`RUNNING`、`PAUSED`、`ERROR` 等；
- 启动、停止和服务重新连接后的恢复策略；
- 全局运行模式互斥约束。

当前阶段继续保持用户选择的模式互斥，除非未来明确设计多业务并行。业务模块不得自行篡改全局运行模式。

### 3.5 `AccountBrowseController / Runtime`

- 是自动浏览业务状态的唯一所有者。
- 保留现有动态识别、卡片筛选、手势、详情页停留、返回、弹窗和恢复规则。
- 重构初期只搬迁代码和状态归属，不重新设计算法。
- 人工接管及恢复属于 AccountBrowse 自身业务状态，不得被 AI_REPLY 的事件处理逻辑误触发。

### 3.6 `AiReplyController / ChatEventController`

- 是 AI 回复流程状态的所有者。
- 管理聊天页面观察、消息处理流程、AI 任务、人工确认和回复发送状态。
- 不直接依赖陌陌 ViewId。
- 不直接持有 `AccessibilityNodeInfo`。
- 不允许绕过消息方向、会话有效性和重复发送检查直接发送。

### 3.7 `MomoChatAdapter`

- 只理解陌陌页面结构和交互方式。
- 负责页面检查、消息节点解析、输入区域定位和具体操作映射。
- 不调用 AI API，不决定 AI 回复内容。
- 不把陌陌专用 ViewId、页面节点结构泄漏给 AI 领域。

### 3.8 `AiProvider`

- 只负责把结构化请求交给具体模型并返回结果。
- 不读取手机界面。
- 不决定是否发送消息。
- 不拥有会话状态或回复队列。

### 3.9 数据状态所有者

- 用户配置由配置 Repository 管理。
- 会话和消息由 Conversation Repository 管理。
- AI 回复任务由 ReplyTask Repository/Queue 管理。
- 运行状态由 RunCoordinator 管理。
- 自动浏览状态由 AccountBrowseController 管理。

**状态所有权规则：**其他模块只通过接口、命令或事件提出请求，不直接修改别的模块内部状态。

## 4. 依赖方向与模块通信规则

1. Domain 不依赖 Android Framework、具体数据库、网络库、模型 SDK 或具体社交应用适配器。
2. Application 层编排业务用例，通过接口调用外部能力。
3. Infrastructure / Adapter 实现接口，不反向控制 Domain 的内部状态。
4. UI 通过 ViewModel/状态容器提交用户意图，不直接访问节点、模型 SDK 或 Repository 的底层实现。
5. `app/AppCompositionRoot` 负责组装依赖，不在其中承载业务规则。
6. 跨领域通信使用公开接口、命令或事件；不得直接修改另一领域的内部字段或状态机。
7. 不得让 AI Reply 直接调用 AccountBrowse 的内部类；不得让 AccountBrowse 直接持有 AI Reply 内部实现。
8. 可以存在与目标结构不同的现有类名，但必须明确其职责映射。不得仅为追求名称一致而进行破坏性改名。

## 5. 无障碍服务完整生命周期与恢复规范

本节是对原架构中服务生命周期、重新连接和恢复职责的工程化补全。它不改变 `FreedomAccessibilityService` 只负责平台生命周期入口的边界。

### 5.1 必须独立记录的状态维度

不得用一个“服务正常/异常”布尔值代表所有状态。至少区分：

1. **应用进程状态**：进程启动、存活、正常退出迹象、异常退出/状态未知。
2. **无障碍授权状态**：是否仍在系统设置中启用 Freedom 的无障碍服务。
3. **悬浮窗授权状态**：是否具备悬浮窗权限。它与无障碍授权是两项独立权限。
4. **服务绑定状态**：未连接、系统绑定中、已连接、正在解绑、已销毁/断开。
5. **服务初始化状态**：未初始化、初始化中、就绪、初始化失败。
6. **运行模式和全局状态**：由 RunCoordinator 所有。
7. **业务任务状态**：由对应业务控制器所有。
8. **手势执行状态**：无手势、排队、执行中、完成、取消、结果未知。

这些状态必须能够分别查询、记录和诊断，不能互相代替。

### 5.2 生命周期事件记录

在平台允许的回调和应用可观测边界内，记录并关联：

- 应用进程启动；
- 服务绑定/连接请求迹象；
- `onServiceConnected`；
- 服务初始化开始、完成、失败；
- 无障碍事件接收与路由异常；
- `onInterrupt`；
- `onUnbind`；
- `onDestroy`；
- 服务重新连接；
- 运行快照读取与恢复；
- 业务任务恢复、拒绝恢复或转入待人工确认；
- 未捕获异常及关键执行失败。

日志至少包含时间、进程/运行会话标识、服务状态、RunMode、RunStatus、任务标识、事件类型和错误原因。敏感消息正文不得为了诊断而无边界写入普通日志。

**平台限制说明：**进程被系统直接终止或崩溃时，应用未必有机会执行最后一次清理回调。因此不能声称所有异常退出都能在发生瞬间被本进程记录；应通过上次运行快照、启动记录和心跳/会话标识，在下一次启动时识别“上次未正常收尾”。

### 5.3 关键回调语义

- `onServiceConnected`：表示服务连接回调到达；不能仅凭此回调就认定业务已经就绪。
- `onInterrupt`：表示服务被系统中断；不能直接等同于服务销毁或无障碍授权丢失。
- `onUnbind`：处理解绑阶段的状态与资源收尾。
- `onDestroy`：处理服务销毁阶段的状态与资源收尾。
- 回调缺失不能被推断为相应生命周期事件从未发生；需结合进程启动时的上次状态核对。

### 5.4 运行快照与恢复

`RuntimeSnapshot` 只保存可安全恢复的业务元数据，例如：

- RunMode、RunStatus 和暂停原因；
- 当前运行会话/代次标识；
- 任务 ID、会话 ID、当前业务阶段和稳定检查点；
- 最近一次状态更新时间；
- 是否存在未完成手势或发送结果未知的操作；
- 是否为用户主动停止。

不得保存并恢复已经失效的 `AccessibilityNodeInfo`、Window/Service 对象或其他短生命周期 Android 对象。

服务重新连接后的顺序：

1. 查询无障碍授权和悬浮窗授权，分别记录结果。
2. 确认服务已连接。
3. 完成服务初始化并建立新的 Gateway/事件路由能力。
4. 读取并校验 RuntimeSnapshot。
5. 确认用户没有主动停止任务。
6. 确认原任务所属模式仍然有效。
7. 重新识别当前包名、页面、窗口和会话；不得沿用断开前的节点对象。
8. 确认业务检查点仍然成立、无未决的危险操作。
9. 由 RunCoordinator 与对应业务状态所有者执行恢复决策。
10. 恢复结果和拒绝原因必须写入日志。

### 5.5 恢复安全条件

只有在以下条件全部满足时，才允许自动恢复：

- 无障碍授权仍有效；
- 服务已连接且初始化完成；
- 原任务不是用户主动停止；
- 模式、任务和目标应用仍然一致；
- 当前页面/会话重新识别成功；
- 检查点仍然有效；
- 不存在发送结果未知、手势结果未知或其他无法安全重放的操作；
- 不会造成同一任务重复启动或重复发送。

任一条件不满足，转入 PAUSED、ERROR 或待人工确认状态，并说明原因。不得为了“自动恢复成功率”而猜测页面、重放未知手势或盲目重发消息。

### 5.6 幂等与并发保护

- 每次运行建立唯一 run/session generation 标识。
- 恢复逻辑必须幂等；重复收到连接、初始化或恢复触发时，不得启动多个相同任务实例。
- 旧代次的异步回调不得修改新代次状态。
- 取消、超时、重连和恢复必须互相协调，避免旧任务在新任务启动后继续执行。
- 恢复前清理或隔离旧的手势队列、事件订阅和回调引用。

### 5.7 平台能力边界

Android 系统可能终止应用进程或改变服务连接状态。Freedom 应实现可观测、可恢复、可校验的机制，但不得承诺应用能够在任何系统状态下强制自行重启服务。若系统没有重新绑定服务或授权确实被撤销，应向用户说明实际状态并要求必要的系统操作；不得将暂时断开误报为必须重新授权。

## 6. 人工接管与自动恢复状态机（AccountBrowse）

本节将既有人工接管/恢复要求转化为可检查的状态机约束。它是对 AccountBrowse 现有规则的保护与工程化，不授权重设原有识别阈值、等待时长、阶段顺序或手势参数。

### 6.1 领域归属

- AccountBrowse 人工接管状态由 AccountBrowseController/Runtime 持有。
- RunCoordinator 负责全局运行状态。
- EventRouter/Policy 负责识别并把相关事件路由到正确领域。
- AI_REPLY 不得进入 AccountBrowse 人工暂停/恢复控制器。
- 不得用一个全局“用户正在操作”标志无差别暂停或恢复所有业务。

### 6.2 状态建议

状态名可以与现有代码命名不同，但语义必须完整：

```text
AUTO_RUNNING
    │ 观察到可信的人工接管信号
    ▼
TAKEOVER_DETECTED
    ▼
PAUSED_FOR_MANUAL
    │ 人工操作持续期间，继续保持暂停
    │ 新人工操作到来时，重新开始静默观察周期
    ▼
WAITING_FOR_MANUAL_QUIET
    │ 达到项目既有静默判定条件
    ▼
REVALIDATING_CONTEXT
    │ 重新检查包名、页面、窗口、列表位置、
    │ 当前阶段和任务检查点
    ├── 校验失败/状态不确定 ──> PAUSED_FOR_MANUAL 或 ERROR
    │
    ▼
RESUME_READY
    │ 由控制器确认没有过期回调或重复任务
    ▼
AUTO_RUNNING
```

另有 `STOPPED`、`ERROR` 等终止/异常状态。实际状态名可以映射现有实现，但不得丢失上述转换语义。

### 6.3 必须保证的行为

1. 每次人工接管都必须独立建立一次暂停—恢复周期，不能只支持第一次接管。
2. 人工操作持续期间不得自动执行浏览手势。
3. 静默观察期间出现新的人工操作信号，应重新开始静默判定。
4. 达到静默条件不等于立即恢复；必须重新校验页面、窗口、业务阶段和检查点。
5. 状态不确定时保持暂停，不得猜测用户已经结束操作。
6. 恢复后必须从有效检查点继续，不得重复完成已执行的阶段动作。
7. 旧暂停周期的延迟任务或回调，不得改变新暂停周期的状态。使用周期 ID/代次标识隔离过期回调。
8. 同一接管信号被多个事件重复报告时，应去重，不能产生多份并发恢复任务。
9. 识别不到人工来源时，不得仅凭一个普通页面内容事件就断言为人工操作；对不确定信号采取保守策略。
10. 不得把服务 `onInterrupt`、服务解绑或进程重启简单当成人工接管事件；这些属于独立生命周期状态。

### 6.4 保护既有算法

人工接管状态机的整理，不授权修改：
- AccountBrowse 阶段顺序；
- 动态识别与卡片筛选逻辑；
- 详情页停留、返回和弹窗处理；
- 已验证的等待时长、阈值、重试次数；
- 手势路径参数；
- 现有人工接管和恢复规则。

如确需修正其中具体行为，必须把该项作为独立变更说明，并取得明确授权。

## 7. 节点检索与事件响应边界（Node & Event Boundaries）

### 7.1 全局节点遍历频次约束

- 禁止在 `onAccessibilityEvent` 回调中无条件、高频次调用 `getRootInActiveWindow()` 并递归遍历整棵节点树。
- 必须通过 `AccessibilityServiceInfo` 在 XML 或代码中严格限定目标包名（`packageNames`）与监听的事件类型（`eventTypes`），不得无差别全景监听手机全局状态。
- 对重复、密集事件进行合并、去重、节流或延迟处理；具体策略需按事件类型和业务需要区分。
- 事件回调内优先做轻量过滤、映射和转发；耗时工作交由受控调度器处理。

### 7.2 节点检索行为约束

- 禁止单一依赖可能随固件或应用版本变化的静态 View ID 锚定核心流程。
- 必须结合文本（`text`）、`contentDescription`、类名（`className`）、父子关系、边界和页面上下文等可用证据进行多维联合校验。
- 循环查找或等待节点出现时，必须设置最大超时阈值和最大重试次数；原文示例为最多重试 5 次，每次间隔采用随机步长。实际参数应尊重当前功能已经验证的配置，不得借本规范擅自修改既有重试次数。
- 节点快照必须有边界：限制遍历深度/节点数/执行时间，记录命中依据和失败原因。
- 不得把 Android 节点对象长期保存到 Domain、Repository、任务队列或 RuntimeSnapshot 中。
- 节点失效、窗口变化或检索超时后，必须重新获取并验证，不得继续使用旧节点引用。

### 7.3 事件映射

事件进入业务前，应尽可能归一化为与 Android API 类型解耦的内部事件；保留必要来源信息、时间戳、目标包名、窗口/页面上下文和事件代次。不同事件类型采用不同策略，不得把页面内容变化、窗口切换、触摸交互和服务生命周期事件混为一类。

## 8. 交互执行与手势通道边界（Interaction & Gesture Boundaries）

### 8.1 屏幕手势唯一通道

- 所有屏幕单击、双击、长按、滑动、滚动、拖动等屏幕交互动作，必须且只能通过 `AccessibilityService.dispatchGesture()` 的物理屏幕坐标手势实现。
- 不得使用 `AccessibilityNodeInfo.ACTION_CLICK`、`ACTION_LONG_CLICK`、`ACTION_SCROLL_FORWARD`、`ACTION_SCROLL_BACKWARD` 或其他节点 Action 替代上述屏幕手势。

这是 Freedom 的项目执行约定，不应误写成 Android 平台禁止所有 Node Action 的通用结论。
 `ACTION_SET_TEXT` 属于文本输入机制，不是屏幕点击/滑动手势的替代方式；其使用仍须遵守第 12 节的输入约束。

### 8.2 手势串行与并发

- 不得在没有并发控制的情况下向 `dispatchGesture()` 派发相互冲突的多条手势。
- 手势按业务时序串行；确需协同的动作必须有明确的并发设计和状态所有者。
- 手势队列应能取消、清空或隔离失效命令。
- 每个 GestureCommand 必须有唯一 ID、运行代次和目标上下文。

### 8.3 回调闭环

所有通过 `dispatchGesture()` 发起的手势，必须实现 `GestureResultCallback`，处理 `onCompleted` 与 `onCancelled`。

- 回调必须闭合对应手势状态机。
- 完成、取消、超时和异常必须产生可追踪结果。
- 旧任务回调不得更新新任务状态。
- `onCancelled` 不代表可以不经检查立即原样重试。
- 发送结果未知或当前窗口已变化时，应停止并重新校验，不得盲目重试。

## 9. 空间几何与触控坐标边界（Spatial & Coordinate Boundaries）

### 9.1 点击坐标、安全内收与空间扰动

1. 禁止固定中心点机械点击
严禁每次都直接获取控件边界矩形（Rect）的绝对中心点（X_center, Y_center），并将其作为固定的最终点击落点重复执行。
控件几何中心可以作为计算坐标的参考基准，但不得把同一个中心像素点无条件作为所有点击操作的最终坐标


2. 规定有效区域内的随机落点：
任何点击动作都必须先确定目标控件当前的有效触控区域，再在该区域内引入高斯分布或均匀分布的随机偏移量。不得在未计算有效区域的情况下直接对屏幕坐标任意加减像素

计算时必须设置安全内边距。例如，可以按照控件边界宽度和高度分别向内收缩约 15%，形成可用采样区域，15% 是常用参考参数，不代表所有尺寸和形状的控件都必须使用同一比例；实际内收量必须保证采样区域仍然有效

3. 随机采样必须受有效区域约束：
- 高斯分布采样应采用截断分布或越界后重新采样；
- 均匀分布采样的上下界必须直接取自安全内收后的有效区域；
- 不得让最终坐标落在控件有效区域之外、屏幕之外或系统手势冲突区域；
- 不得通过简单裁剪使大量采样结果堆积在边界上，造成新的坐标偏差。

如果控件过小、不规则或内收后没有有效采样区域，应重新计算该控件的实际有效触控区域；仍无法得到可靠落点时，停止该次点击并报告原因，不得退回到未经校验的固定中心点点击。

### 9.2 滑动轨迹非线性约束
1. 禁止使用两点直线插值生成滑动轨迹：
- 严禁使用两点之间的直线插值（Linear Interpolation）作为滑动或拖动操作的空间轨迹。

2. 规定贝塞尔曲线轨迹：
- 所有滑动与拖动操作必须通过二次或三次贝塞尔曲线生成轨迹，并根据动作起点、终点、方向和操作区域设置动态控制点。不得用简单的两点直线插值代替规定的曲线路径。

3. 补充时间参数化与速度曲线：
贝塞尔曲线定义的是空间路径形状，本身并不自动产生加速、匀速和减速效果。为实现原文要求的平滑运动过程，必须同时为轨迹配置时间参数化或速度曲线，明确：
- 起始阶段的加速过程；
- 中间阶段的速度变化或相对平稳区间；
- 结束阶段的减速过程；
- 总持续时间及采样点的时间分布。

路径几何与时间变化必须共同生成最终 GestureDescription，不能只生成贝塞尔路径而忽略执行时间，也不能只调整持续时间而仍使用固定直线匀速轨迹。

## 10. 时间节律与操作频次边界（Temporal Rhythm Boundaries）

### 10.1 固定延时与概率分布约束
1. 禁止连续操作长期依赖固定硬编码延时：
严禁把固定不变的毫秒级延时作为连续操作步骤之间的通用等待策略，例如所有步骤一律使用 Thread.sleep(1000)。不得让连续操作长期按照完全相同的固定间隔机械执行。

2. 规定交互等待时间的概率分布：
交互前后的停顿、等待和决策间隔必须采用有边界的概率分布生成，并根据任务类型配置分布参数。生成的等待时间必须满足预设的最小值、最大值和超时限制，不得出现负数或无上限等待。

3. 概率模型必须与所描述的量相匹配：
- 泊松分布适合描述给定时间区间内事件发生的次数，不应直接把泊松分布的取值当作连续等待时长。
- 在泊松过程假设下，事件间隔可以使用指数分布建模；需要控制等待时间范围时，应进行截断或采用有界模型。
- 带权高斯或截断正态分布可以用于生成围绕设定均值波动的等待时间，但必须设置有效上下限。
- 也可以根据任务的等待特征使用其他非负、有界的连续概率分布，例如 Gamma 或对数正态分布；必须说明选择依据和参数范围。

上述模型用于生成受控的操作间隔和任务等待时间，不得将某一种分布本身表述为必然符合真实人类反应时间的保证。

固定时间值可以用于明确的超时阈值、系统接口要求或经过验证的业务时限；但不得以此取代本规范要求的常规交互间隔分布机制。

### 10.2 操作频次与阶段节律约束

1. 禁止瞬时高频连击：
严禁在极短时间窗口内集中派发大量相同密度的交互动作。必须设置单阶段操作数量、操作间隔和连续执行边界，避免无控制地连续触发。

2. 规定操作节律分段：
必须将长周期任务拆解为多个阶段，并在阶段之间引入大跨度的宏观停顿。阶段停顿应作为任务流程中的明确步骤，用于页面状态观察、任务阶段确认、必要的内容检查和资源释放，不得将长周期任务压缩成无间隔的连续操作。

阶段停顿同样应有明确的时间范围、状态检查条件和超时处理；不能只等待固定时间而不检查当前任务是否仍处于预期状态。

## 11. 滑动起止点坐标约束

### 11.1 起点与终点不得机械固定

1. 禁止起点固定：
严禁每次滑动或滚动操作都从完全相同的固定绝对坐标起笔，例如始终从屏幕正中央或某个固定控件的绝对中心点开始。

2. 禁止终点固定：
严禁每次滑动都无视当前页面视口、滚动容器边界和目标滚动幅度，将终点固定在同一个死板的像素坐标上。

### 11.2 起点随机扰动
- 所有滑动操作的起点（X_start, Y_start）必须以当前有效滑动区域内确定的基础基准坐标为基础，引入正态随机偏移。原文给出的 ±15～25 像素可作为初始扰动范围，具体取值应根据屏幕分辨率、有效滑动区域和操作类型配置。

- 随机偏移必须采用受边界约束的采样方式。采样后若超出有效滑动区域，应重新采样或在有效范围内重新计算允许的扰动区间，不得直接使用越界坐标，也不得静默取消本项随机扰动要求。

### 11.3 滑动距离与终点动态浮动

- 滑动距离和终点（X_end, Y_end）必须结合当前页面实际视口、滚动容器或目标控件边界计算，并在基础滑动距离上引入动态步长浮动。原文给出的 ±5%～10% 可作为初始浮动范围。

- 每次浮动后的终点都必须经过边界校验，确保仍在有效滑动区域内，并符合当前滚动方向和业务目标。若采样结果越界，应重新采样或重新计算当前允许的浮动范围，不得直接使用越界坐标。

- 在有效区域和任务目标允许的范围内，滑动起点、路径长度和落点应按设定范围产生变化，避免所有滑动都使用相同起点、相同距离和相同终点。随机变化必须受页面几何边界约束，不得以坐标差异为由牺牲操作有效性

## 12. 输入通道与输入节奏控制（Input Channel & Input Cadence）

### 12.1 输入方式与禁止行为

1. 禁止批量填充后立即发送：
不得通过 AccessibilityNodeInfo.ACTION_SET_TEXT 或剪贴板一次性将一大段文字填充进输入框。

### 12.2 分段输入停留要求

1. 分段输入：
对目标应用的输入框，必须将一段文字拆成多个小段，逐段更新输入框，每段文字必须在输入框中加入随机浮动的停留时间，不得把所有内容无条件地作为一个瞬时输入步骤处理。

- 这段停留时间必须用于实际的内容检查和确认，包括检查错别字、内容完整性、文本是否截断或异常，以及输入框是否仍处于预期会话。不得在填充完成后立即点击发送，也不得把等待时间结束本身当作自动发送条件。
- 完成必要的检查和确认后，才允许进入发送步骤。若检查发现内容不正确、输入框状态变化或当前会话不确定，应停止发送并转入相应异常处理流程。

### 12.3 发送按钮坐标约束
- 发送按钮（Send Button）的点击同样必须遵守空间几何与触控坐标约束。必须基于发送按钮当前有效边界计算落点，并在有效触控区域内应用高斯分布或均匀分布的合理随机坐标扰动。
- 严禁每次点击都无条件使用完全相同的固定像素坐标。随机偏移必须受按钮有效触控区域及安全内边距约束，不能因随机扰动导致落点偏离按钮或触发邻近控件。

## 13. 状态机与防重复机制（Stateful Memory & Cooldown）

### 13.1 重复回复约束

禁止对同一目标对象或同一聊天上下文中的同一回复任务，在短时间内重复触发相同的回复逻辑。

防重复判断必须区分“同一条消息的重复处理”和“同一用户后来发送的新消息”。不得仅因为用户 ID 相同，就把该用户后续所有新消息都当成重复消息。


### 13.2 本地短期记忆缓存（Memory Buffer）

必须建立本地短期记忆缓存，记录最近已处理或已回复的对象和内容。原文要求记录的用户 ID 与话术哈希必须保留，不得被其他字段替代。

在此基础上，建议同时记录：
- 目标应用标识；
- 当前账号标识；
- 会话或聊天上下文标识；
- 用户 ID；
- 接收消息 ID（目标应用能够提供时）；
- 回复话术哈希；
- 回复任务唯一标识；
- 任务创建时间、处理时间和冷却到期时间；
- 当前任务状态及发送结果。

去重判断应结合用户 ID、会话上下文、消息标识和话术哈希等信息，避免因单一字段相同而误判不同消息。

### 13.3 冷却时间（Cooldown）与任务状态

必须设置明确的冷却时间，避免在设定周期内对同一特征对象或同一回复任务产生机械化的重复响应。冷却时间应有清晰的作用范围、起算时点和到期条件。

对回复任务至少区分以下状态：待处理、正在执行、已完成、执行失败、发送结果未知。收到重复事件时，必须先检查 Memory Buffer 和任务状态；已完成或正在执行的同一任务不得再次启动。

对于发送结果未知的任务，必须先确认实际发送状态，再决定是否重试。不得在没有确认的情况下盲目重复发送。

## 15. AI Reply 业务边界与发送安全

1. AI Reply 必须独立于 AccountBrowse。
2. AI Feature 不得直接调用 Android Service 或其他 Feature 的内部类。
3. Momo 适配器负责页面结构、消息解析、输入位置和动作映射；不得决定 AI 回复内容。
4. AiProvider 只负责结构化模型请求与返回结果；不得读取页面或决定是否发送。
5. 会话和消息由 Conversation Repository 管理；回复任务由 ReplyTask Repository/Queue 管理。
6. 群聊、图片、语音、视频、系统通知以及无法确认消息方向的消息，不得自动回复。
7. 消息方向、发送者或会话身份存在不确定性时，停止自动回复。
8. 会话切换、页面变化、消息批次过期或发送目标不一致时，必须重新校验。
9. 发送结果未知时，进入待核验状态，不得猜测发送成功或盲目重试。
10. AI 回复任务应具有明确的状态转换和幂等 ID，不得因事件重复到达而重复调用模型或重复发送。

## 16. 日志、诊断与可测试性

1. 关键状态转换必须记录：旧状态、新状态、原因、触发事件、任务 ID、运行代次和时间。
2. 节点检索记录命中证据、失败类型和耗时，不应只记录“找到/没找到”。
3. 手势记录 GestureCommand ID、坐标上下文、派发结果、回调结果和取消原因。
4. 人工接管记录每一轮接管周期 ID、暂停原因、静默判定、恢复校验结果和最终动作。
5. 服务生命周期记录应区分权限、绑定、初始化和业务运行状态。
6. 日志不得依赖单一自由文本；关键状态应使用可检索的结构化字段。
7. 时间、随机数、调度器和平台 Gateway 应尽可能通过接口注入，便于单元测试。
8. Domain 和 Application 应能在不启动真实 Android Service 的条件下测试核心规则。
9. 不得为了方便测试而将生产状态所有权转移给测试辅助类。

## 17. 代码保护与变更纪律

### 17.1 修改前

每次修改前必须：

1. 阅读本文件中与任务相关的架构边界和保护规则。
2. 检查当前源码，确认实际类、调用链、状态所有者和已有测试。
3. 区分“目标组件”与“当前实现类”，建立映射，不得凭类名猜测功能。
4. 确认变更范围及其对现有默认配置、持久化、权限、广播、UI 和业务算法的影响。
5. 对超出用户任务范围的改动保持克制，不顺手重构无关模块。

### 17.2 修改中

- 不破坏 Freedom 现有能力、默认配置、UI 交互和运行逻辑；逐步增加业务。
- 不重写 AccountBrowse 算法。
- 不改变阶段顺序、识别阈值、延时、重试次数、手势路径参数、人工接管和恢复规则，除非该项变更被独立确认并记录。
- 不改变现有持久化 key、默认开关、权限声明、广播 Action 和既有 UI 交互，除非该阶段明确需要且有单独验证。
- 不为架构整齐而一次性搬迁大量文件。
- 新增代码应有清晰职责、单向依赖、可测试边界和易懂的中文注释。
- 不创建没有实际用途的大量空目录、空接口或空类。
- 不将不同业务领域的状态塞入一个全局可变对象。
- 不得以删除规划中的组件、职责或目录来掩盖当前源码与目标架构的差距。

### 17.3 修改后

必须完成与改动规模相匹配的验证，并报告：

1. 修改文件及每个文件的实际变更；
2. 对应的目标架构组件；
3. 原有行为是否保持；
4. 新增或调整的状态转换和调用链；
5. 执行的测试、构建命令及其结果；
6. 未能验证的部分及原因；
7. 当前源码与目标架构仍存在的差距。

测试失败或构建未完成时，必须如实说明，不得声称已通过。

### 17.4 必须独立确认的重大变更

以下变更不得作为普通整理顺手实施：
- 改变 AccountBrowse 已验证算法或用户可观察行为；
- 改变全局 RunMode 互斥规则；
- 改变人工接管/恢复判定；
- 改变持久化 key、数据结构兼容策略或消息去重语义；
- 改变权限声明、广播 Action、默认开关或现有 UI 交互；
- 改变手势唯一执行通道、坐标算法或可视化强制要求；
- 将当前单体提前拆分为多个 Gradle Module；
- 删除或合并目标架构中的规划组件。

## 18. Agent 执行完成的验收标准

一项工程任务只有在下列适用条件得到核对后，才可报告完成：
- [ ] 当原文的技术实现方式存在问题时，应该修正实现方式，而不是直接取消它所要达到的工程目标
- [ ] 不得删减或弱化目标架构。
- [ ] 变更没有突破领域职责边界和状态所有权。
- [ ] FreedomAccessibilityService 未承载业务状态机或 AI 业务逻辑。
- [ ] 无障碍权限、悬浮窗权限、服务绑定、初始化和业务运行状态没有混为一谈。
- [ ] 节点检索有包名/事件过滤、频率边界、超时和失败处理。
- [ ] 所有屏幕手势通过 `dispatchGesture()` 执行，并处理完成/取消回调。
- [ ] 点击、轨迹、时间和起止点参数遵守本规范。
- [ ] 输入流程包含文本校验和发送结果核验。
- [ ] Memory Buffer 保留用户 ID 与文本哈希，Cooldown 和 UNKNOWN 状态可用。
- [ ] 自动手势有实时可视化，预览与执行共用同一命令数据。
- [ ] 人工接管每一轮都能独立暂停、静默判断、重新校验和恢复。
- [ ] AI_REPLY 与 ACCOUNT_BROWSE 保持隔离。
- [ ] 群聊、媒体消息、系统通知和方向不确定消息不会自动回复。
- [ ] 没有改变未经授权的现有功能、配置和交互。
- [ ] 测试、构建及未验证项如实报告。
